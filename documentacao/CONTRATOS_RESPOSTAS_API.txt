QUESTÃO 3 — MANIPULAÇÃO E VALIDAÇÃO DAS RESPOSTAS DA API
Transparência Brasil | Implementação de Response Models

1. FINALIDADE

A integração local com o Qwen já permite enviar textos e obter resumos ou explicações pela FastAPI. Nesta etapa, o objetivo foi tornar explícitas as regras que definem quais dados podem entrar na API e como os resultados devem ser devolvidos. Dessa forma, o Streamlit recebe informações com campos e tipos previsíveis, em vez de depender de um JSON cujo formato poderia mudar silenciosamente.

2. ESTRUTURA IMPLEMENTADA

O módulo api/schemas/ia.py contém os modelos Pydantic RequisicaoTexto, RespostaTexto e StatusModelo. A rota POST /processar_texto recebe RequisicaoTexto e declara response_model=RespostaTexto. A rota GET /ia/health declara response_model=StatusModelo. Também foram formalizadas as respostas das rotas gerais: despesas, estatísticas, conteúdo Web e saúde da API. Os contratos dos dados oficiais Siconfi foram mantidos.

O contrato da requisição exige um texto com conteúdo legível de até 12.000 caracteres. São aceitas duas operações: resumo e explicacao. A quantidade máxima de novos tokens deve ser um número inteiro entre 32 e 512. Textos vazios, campos extras, tipos inadequados e operações desconhecidas produzem HTTP 422 antes de o Qwen ser acionado.

A resposta de processamento contém os seguintes campos obrigatórios: operacao, texto_original, resultado, modelo, execucao_local, tokens_entrada, tokens_saida, tempo_processamento_ms e aviso. O resultado precisa ser um texto não vazio, as contagens de tokens devem ser inteiros positivos, o tempo de processamento não pode ser negativo e o indicador de execução local precisa ser verdadeiro. Assim, uma saída vazia ou estruturalmente inconsistente não é entregue como sucesso.

A documentação interativa do FastAPI, disponível em /docs, apresenta os formatos de entrada e saída automaticamente a partir desses modelos. A validação é feita pelo Pydantic v2, e os campos inesperados são rejeitados nos modelos específicos da integração com IA.

3. EXEMPLO DE REQUISIÇÃO VÁLIDA

POST http://127.0.0.1:8000/processar_texto
Content-Type: application/json

{
  "texto": "A transparência pública facilita o acompanhamento das despesas governamentais.",
  "operacao": "resumo",
  "max_novos_tokens": 128
}

A resposta HTTP 200 contém o texto gerado e os metadados descritos anteriormente. O conteúdo e o tempo exatos dependem da inferência real realizada localmente; não há resposta ou tempo fixo previamente atribuído.

4. EXEMPLO DE REQUISIÇÃO INVÁLIDA

{
  "texto": "   ",
  "operacao": "resumo",
  "max_novos_tokens": 128
}

O esperado é HTTP 422, acompanhado da identificação do campo incorreto. Nenhum processamento na GPU deve ser iniciado para essa entrada. Outras situações testadas incluem operação não permitida, limite de tokens fora da faixa, número de tokens enviado como texto e campo inesperado.

5. VALIDAÇÃO DE SAÍDA

Não basta validar o que o usuário envia. O servidor também verifica o que devolve. Por exemplo, uma geração que retorne somente espaços ou uma contagem de tokens do tipo texto viola o contrato da resposta. Nesses casos, o sistema não deve publicar a resposta como HTTP 200. O comportamento é coberto por testes automatizados, inclusive com simulação de saída inválida.

A validação assegura consistência estrutural, não exatidão factual. Uma resposta pode obedecer integralmente ao formato JSON e ainda conter um erro de interpretação. A qualidade do conteúdo continua exigindo análise das fontes e testes funcionais. Os controles de timeout, concorrência e outros erros serão aprofundados na questão seguinte.

6. ARQUIVOS MODIFICADOS OU CRIADOS

- api/schemas/ia.py: regras de entrada e saída do processamento e do estado do Qwen;
- api/schemas/geral.py: contratos de saúde, estatísticas e catálogo Web;
- api/main.py: aplicação de response_model a rotas antes não tipadas e aprimoramento dos campos fiscais;
- tests/test_contratos_resposta.py: testes de campos, tipos, limites e contrato OpenAPI;
- documentacao/API.md: atualização da documentação técnica;
- README.md: registro das alterações desta etapa;
- .gitignore: exclusão do pacote temporário e do backup local do controle de versão.

7. COMO TESTAR NO WINDOWS

Entre na pasta do projeto e use o mesmo ambiente virtual em que instalou o Qwen. Não é necessário reinstalar bibliotecas ou baixar modelos.

Teste completo:
.\.venv\Scripts\python.exe -m pytest -q

Teste específico desta questão:
.\.venv\Scripts\python.exe -m pytest -q tests/test_contratos_resposta.py

Se o ambiente se chamar .venv_tp4, substitua .venv pelo nome correto. A versão de referência passou em 116 testes automatizados no ambiente de desenvolvimento. Os testes não usam o Qwen de verdade; verificam a API e os contratos com um serviço simulado.

Para a comprovação end-to-end, mantenha a FastAPI em execução:
.\.venv\Scripts\python.exe -m uvicorn api.main:app --host 127.0.0.1 --port 8000 --workers 1

Acesse http://127.0.0.1:8000/docs, abra POST /processar_texto e teste as duas requisições acima. A válida deve retornar 200 com todos os campos; a inválida deve retornar 422. Depois, inicie o Streamlit em outro terminal e faça um resumo pelo Assistente IA para confirmar que o contrato atualizado não interrompeu a integração real.

8. RESULTADO E LIMITAÇÕES

O projeto agora define contratos claros para os dados recebidos e enviados pela FastAPI. A validação impede que entradas inconsistentes acionem o Qwen e evita que saídas malformadas sejam tratadas como respostas corretas. Os testes comprovam o comportamento do software no ambiente de desenvolvimento, enquanto a verificação do Qwen na GPU continua sendo feita no computador local. As estruturas anteriores, incluindo os dados ilustrativos, os dados oficiais e o ambiente do modelo, foram preservadas.
